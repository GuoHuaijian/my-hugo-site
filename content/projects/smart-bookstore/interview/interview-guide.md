# 面试讲解指南

> 如何用5分钟讲清楚这个项目，让面试官印象深刻

## 1. 项目介绍话术（30秒）

### 1.1 开场白

> "我做的是一个企业级分布式秒杀系统，叫BookStore智慧书城。这个项目以**商品秒杀下单**为核心业务线，将主流的分布式技术完整串联到一次请求的全生命周期中。"

### 1.2 核心数据

> "系统设计目标是支撑**1万QPS**的秒杀请求，通过**多级限流**、**异步削峰**、**分布式缓存**等手段，实现毫秒级响应。"

---

## 2. 架构讲解（1分钟）

### 2.1 画图辅助
```
     用户
      │
      ▼
┌──────────┐
│  Gateway │ ← 限流、认证
└────┬─────┘
     │
┌────┴────┐
│ Seckill │ ← 校验、Redis预减
└────┬────┘
     │ MQ
┌────┴────┐
│  Order  │ ← Seata事务
└────┬────┘
     │ Dubbo
┌────┴────┐
│Inventory│ ← 乐观锁
└─────────┘
```

### 2.2 讲解话术

> "系统采用微服务架构，核心有6个服务。请求从**Gateway网关**进入，经过JWT认证和Sentinel限流后，到达**秒杀服务**。"

> "秒杀服务做校验和Redis预减库存后，通过**RocketMQ**异步发送创建订单的消息。**订单服务**消费消息，开启**Seata分布式事务**，创建订单并调用**库存服务**扣减库存。"

> "订单和库存使用**ShardingSphere**做分库分表，库存扣减使用**乐观锁**防止超卖。"

---

## 3. 核心亮点（2分钟）

### 3.1 亮点一：多级限流

> "我们做了**三级限流**设计：第一级是网关层，基于Sentinel做API级别的QPS限流；第二级是服务层，做资源级别的限流；第三级是热点参数限流，防止某个热门商品被刷爆。"

```
网关限流: 10000 QPS (全局)
↓
服务限流: 1000 QPS (单机)
↓
热点限流: 500 QPS (单商品)
```

### 3.2 亮点二：库存防超卖

> "防止超卖是秒杀的核心问题，我们用了**双重保障**：第一层是Redis预减库存，使用**Lua脚本**保证原子性；第二层是数据库的**乐观锁**，即使Redis有问题也不会超卖。"

```lua
-- Lua脚本核心逻辑
if stock >= quantity then
    redis.call('DECRBY', key, quantity)
    return 1
else
    return -1
end
```

### 3.3 亮点三：异步削峰

> "秒杀瞬时会有大量请求，我们通过RocketMQ异步处理。Redis预减成功后立即返回'排队中'，用户感知的响应时间在50ms以内。后端MQ消费者按照自己的节奏处理订单，实现了削峰填谷。"

```
请求: 10000 QPS → MQ缓冲 → 消费: 500 QPS
```

### 3.4 亮点四：分布式事务

> "订单创建和库存扣减涉及两个服务的数据库，我们使用Seata AT模式保证分布式事务。它的好处是对业务代码侵入很小，只需要一个@GlobalTransactional注解。"

---

## 4. 技术深度展示（1分钟）

### 4.1 遇到的问题与解决

> "开发过程中遇到一个问题：分布式锁和Redis预减库存的执行顺序。"

> "如果先加锁再预减库存，锁的粒度太大，会成为性能瓶颈；如果先预减库存再加锁，可能出现库存扣了但锁获取失败的情况。"

> "最终的方案是：先预减库存，预减成功后再加锁。如果加锁失败，在异常处理中回滚Redis库存。这样既保证了性能，又保证了正确性。"

### 4.2 性能优化点

> "性能方面做了几个优化：一是本地缓存活动信息，减少Redis访问；二是售罄后快速失败，直接读Redis标记不走后续逻辑；三是责任链模式实现校验链，任何一步失败立即返回。"

## 5. 面试官常问问题

### Q1：为什么用Dubbo不用Feign？
"两点考虑：一是性能，Dubbo基于TCP长连接，比HTTP短连接性能更好，在秒杀这种高并发场景更合适；二是功能，Dubbo有更丰富的负载均衡策略和服务治理能力。"

### Q2：如何保证消息不丢失？
"从三个层面保证：生产端用同步发送+失败重试；Broker端用同步刷盘+主从同步；消费端用手动ACK+消费幂等。"

### Q3：如果Redis挂了怎么办？
"首先，Redis我们用的是Cluster集群模式，本身有高可用保障。如果真的不可用，系统会降级处理：限流规则会拦截大部分请求，少量请求直接查数据库库存，依靠数据库的乐观锁保证不超卖。"

### Q4：分库分表后如何查询？
"我们的分片键是user_id，用户查询自己的订单直接走分片，性能没问题。管理后台需要跨分片查询时，通过订单号定位（订单号包含用户信息），或者通过ES同步实现全量搜索。"

### Q5：Seata事务超时怎么处理？
"Seata有超时自动回滚机制，我们设置的超时时间是30秒。如果超时，TC会通知各分支事务回滚。同时，我们在MQ消费失败时也有补偿逻辑，回滚Redis库存和已购标记。"

## 6. 加分话术

### 6.1 技术选型思考
"选型时我们做过对比调研，比如分布式事务对比了Seata、DTX、本地消息表，最终选择Seata是因为社区活跃、阿里背书、AT模式对业务无侵入。"

### 6.2 代码规范
"代码完全遵循阿里巴巴Java开发手册，包括命名规范、异常处理、日志规范等。"

### 6.3 可观测性
"系统接入了SkyWalking做链路追踪，每个请求都有TraceId，从网关到数据库全链路可追溯，线上问题排查非常方便。"

### 6.4 持续学习
"这个项目让我对分布式系统有了更深的理解，特别是一致性和可用性的权衡。我也在持续学习，比如最近在研究Seata Saga模式和Service Mesh。"
