# 技术栈详解

## 3. 技术选型理由

### 3.1 微服务选择Dubbo而非Feign
- **性能**：Dubbo基于TCP长连接，比HTTP短连接性能更好
- **功能**：Dubbo有丰富的负载均衡策略和服务治理能力
- **生态**：成熟的开源项目，社区活跃

### 3.2 分布式事务选择Seata AT模式
- **低侵入**：只需一个注解，业务代码无需修改
- **高性能**：AT模式相比TCC性能更好
- **易维护**：自动补偿机制，无需手写回滚逻辑

### 3.3 消息队列选择RocketMQ
- **事务消息**：支持分布式事务
- **延迟消息**：支持订单超时等场景
- **高可靠**：主从架构、同步刷盘

### 3.4 分库分表选择ShardingSphere-JDBC
- **透明化**：业务代码无需修改
- **轻量级**：客户端分片，无需额外部署
- **功能丰富**：支持读写分离、分片策略灵活

## 4. 技术架构演进

### 4.1 架构演进图
```
单体应用
    ↓
微服务架构（服务拆分）
    ↓
服务治理（Nacos + Dubbo）
    ↓
分布式能力（Redis + MQ + Seata）
    ↓
可观测性（SkyWalking）
    ↓
持续优化（性能 + 高可用）
```

### 4.2 技术演进路线

| 阶段 | 特点 | 挑战 | 解决方案 |
|------|------|------|----------|
| 初期 | 单体应用 | 快速开发 | 分层架构 |
| 成长期 | 微服务拆分 | 服务治理 | Nacos注册 |
| 成熟期 | 高并发 | 性能瓶颈 | 缓存优化 |
| 稳定期 | 高可用 | 故障恢复 | 容错设计 |

## 5. 技术债务与优化

### 5.1 当前技术债务
- 某些服务设计不够灵活，扩展性受限
- 缺少完整的单元测试覆盖
- 日志标准化程度有待提高

### 5.2 未来优化方向
- 引入Service Mesh，实现服务治理下沉
- 完善监控告警体系，实现主动运维
- 考虑引入CQRS模式，优化读写性能
