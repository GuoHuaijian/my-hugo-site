# 深度追问应对

> 面试官追问套路与应对策略

## 1. 数据一致性追问

### Q: 如果 Seata TC 宕机了怎么办？

**应对思路**：
```
TC 宕机 → 分支事务未完成 → 全局事务悬挂

解决方案：
1. Seata Server 集群部署，保证 TC 高可用
2. 业务侧定时轮询未完成事务，手动补偿
3. 配合 MQ 最终一致性，非关键路径不强依赖 Seata
```

### Q: 你说用了 Seata AT 模式，undo_log 什么时候清理？

**应对思路**：
```
1. 全局提交时：立即删除 undo_log（只需要删除即可）
2. 全局回滚时：根据 undo_log 回放数据后删除
3. 异常情况：定时任务清理过期 undo_log
```

### Q: AT 模式和 TCC 模式怎么选？

**应对思路**：
```
AT 模式：
- 适用于大多数场景
- 侵入性低，一个注解搞定
- 性能适中，需要记录 undo_log

TCC 模式：
- 适用于高性能场景
- 需要手写 Try/Confirm/Cancel 三段逻辑
- 无需写 undo_log，性能更好

选型建议：优先 AT，性能敏感场景用 TCC
```

## 2. 高并发追问

### Q: 100 万人同时抢 100 件商品，你的系统能扛住吗？

**应对思路**：
```
预估流量：
- 100 万人 × 10% 转化率 = 10 万 QPS
- 网关层限流 10000 QPS，大部分请求在网关层被拒绝
- 秒杀服务 3 个实例 × 1000 QPS = 3000 QPS
- MQ 削峰到 500 QPS 平稳消费

核心逻辑：
1. 大部分请求在网关就被限流拒绝了
2. 进入秒杀服务的请求经过层层校验过滤
3. 最终只有 100 人能成功，其他都是"排队中"
```

### Q: 你怎么保证 100 件商品不会被多卖？

**应对思路**：
```
1. Redis Lua 原子扣减（第一道防线）
   - 库存为 0 时自动设置售罄标记
   - Lua 脚本保证扣减原子性

2. 数据库乐观锁（兜底防线）
   - UPDATE ... WHERE version = ?
   - 版本号不匹配说明已被其他线程修改

3. 最终一致性保证
   - 超卖的订单会回滚
   - 补偿机制释放 Redis 库存
```

### Q: 限流了怎么保证用户体验？

**应对思路**：
```
1. 友好的返回提示："系统繁忙，请稍后再试"
2. 排队机制：进入 MQ 就返回"排队中"，前端轮询结果
3. 引导策略：错峰限流，分时段开放秒杀
4. 用户体验优化：预估等待时间，实时显示排队位置
```

## 3. 分库分表追问

### Q: 分片键选错怎么办？

**应对思路**：
```
1. 分片键一旦确定，后期很难修改
2. 选型原则：按查询最多的维度做分片键
3. 本项目中：
   - 订单表按 user_id 分片（用户查订单最多）
   - 库存表按 product_id 分片（库存操作针对商品）
4. 如果选错，只能新建表迁移数据
```

### Q: 分库分表后怎么做跨分片查询？

**应对思路**：
```
1. 禁止跨分片 JOIN（性能差）
2. 使用绑定表优化关联查询
3. 全局表：数据量小的表不做分片，各分片都有
4. 汇总查询：ES 或宽表做查询
5. 二次查询：先查各分片再聚合结果
```

## 4. MQ 追问

### Q: RocketMQ 消息顺序怎么保证？

**应对思路**：
```
1. 使用 MessageQueueSelector
2. 相同业务 ID（如订单号）发到同一个 Queue
3. 一个 Queue 只有一个消费者消费
4. 缺点：并发度降低
```

### Q: RocketMQ 的事务消息原理？

**应对思路**：
```
1. 发送 half 消息（对消费者不可见）
2. 执行本地事务
3. 提交/回滚消息
4. 如果本地事务结果未返回，RocketMQ 回查
5. 根据回查结果决定最终投递或删除
```

## 5. 分布式锁追问

### Q: Redisson 看门狗机制原理？

**应对思路**：
```
1. 获取锁成功后启动定时任务
2. 每 10 秒检查一次锁是否还在持有
3. 如果还在持有，自动续期 30 秒
4. 业务完成后释放锁，取消定时任务
5. 防止业务未完成锁提前过期
```

### Q: Redis 主从切换时锁丢失怎么办？

**应对思路**：
```
1. Redlock 算法：在多个 Redis 节点同时加锁
2. 实际生产中：
   - Redis Sentinel 切换后会有短暂不可用
   - 业务侧做好幂等处理
   - 锁的超时时间设置合理
   - 大部分场景不需要 Redlock（性能代价大）
```

## 6. 系统设计追问

### Q: 如果让你重新设计这个系统，你会怎么做？

**应对思路**：
```
1. 架构层面：引入 K8s 实现自动弹性伸缩
2. 性能层面：
   - 引入多级缓存（Caffeine + Redis）
   - 商品详情页静态化到 CDN
3. 可观测性：完善全链路压测和容量评估
4. 容灾：多活部署，同城双活
```

### Q: 这个项目最大的技术挑战是什么？

**应对思路**：
```
最大挑战是"一致性"和"性能"的平衡：
1. 秒杀要求高并发，但库存扣减必须准确
2. Seata 保证强一致性但会降低性能
3. 通过异步削峰实现了性能的提升
4. 通过 Seata AT 模式保证了数据的强一致性
5. 整体方案在性能和一致性之间取得了平衡
```
